# Terminal Deck — Android client

A phone-sized window onto sessions already running on your Mac. It lists them and renders one; it
does not run a shell on the phone and has no ambition to.

Application id `dev.terminaldeck.apk` (the Play package; the code namespace stays `dev.terminaldeck.android`). Kotlin + Jetpack Compose for the chrome, Termux's
`TerminalView` for the terminal itself, a Kotlin port of `src/shared/sealed.ts` for the wire.

## Build and run

There is no system JDK on the usual dev Mac here, and there does not need to be — Android Studio
bundles one:

```sh
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
cd android
./gradlew :app:assembleDebug            # → app/build/outputs/apk/debug/app-debug.apk
./gradlew :app:testDebugUnitTest        # crypto interop, protocol codec, pairing codes, key bar
```

`local.properties` needs `sdk.dir=$HOME/Library/Android/sdk`; it is gitignored, so a fresh clone
writes its own.

On an emulator:

```sh
~/Library/Android/sdk/emulator/emulator -avd <avd> -no-window -no-snapshot -gpu swiftshader_indirect &
adb wait-for-device
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n dev.terminaldeck.apk.debug/dev.terminaldeck.android.MainActivity
adb exec-out screencap -p > shot.png
```

Note the `.debug` suffix on the component name — debug builds carry `applicationIdSuffix = ".debug"`
so a debug build and a release build can sit on the same device.

## Layout

```
app/
  crypto/                Noise IK, ported from src/shared/sealed.ts
  store/                 the device's key and credential, wrapped by the Android Keystore
  pairing/               the pairing code and the only place its text is believed
  protocol/              the wire language, transcribed from src/main/remote/protocol.ts
  transport/             the relay socket, the sealed channel, the reconnect schedule
  session/               joins a Termux emulator to the transport
  ui/                    pair screen, session list, terminal, key row, theme
terminal-view/           vendored from Termux, Apache 2.0, unmodified
terminal-emulator/       vendored from Termux, Apache 2.0, one file modified
tools/                   the verification rig — a stand-in Mac and the crypto fixtures
```

`VENDORED.md` and `MODIFICATIONS.md` are the licence paperwork and are not optional reading before
touching either vendored directory — the repository they come from is GPLv3 apart from these two
modules.

## How a connection is made

```
   pairing code  →  terminaldeck://pair#h=<host id>&k=<Mac's X25519 key>&t=<one-shot token>&r=<relay>
   GET <relay>/v1/join?host=<26-char host id>          the only thing the relay is ever told
   → 81 bytes   [0x01] e ‖ seal(s)                     Noise IK message one, behind its version
   ← 49 bytes   [0x01] e ‖ seal(empty)                 message two
   ⇄ sealed frames, each one a protocol.ts JSON message
```

The relay is treated as hostile by construction: it sees a host name and ciphertext. The 17-byte
envelope in `relay/src/rendezvous.ts` is host-side only, so nothing on the phone writes one.

**The version byte is not optional, and this README used to say 80 and 48.** `src/shared/sealed.ts`
produces the 80- and 48-byte Noise messages; `src/shared/relay-wire.ts` frames each with one version
byte before it crosses a relay. The client had the first file ported and not the second, so it sent
80 bytes — and a desktop refuses a first payload of the wrong length by closing the channel in
silence, deliberately, so that a hostile relay gets no oracle out of a refusal. The result was a
handshake that never completed and a phone that said the Mac was asleep. `protocol/RelayWire.kt` is
that framing, `RelayWireTest` pins the byte counts against numbers generated by running the real
module, and `tools/dev-host.cjs` now imports the desktop's own `withSealedVersion` /
`readSealedHandshake` rather than re-deriving them — it skipped the byte too, which is why nothing
caught this.

**Pairing** is two steps, because a token can be read over a shoulder. The first `hello` spends the
one-shot token and comes back with a durable credential *and* a refusal — `device-auth.ts` will not
admit a device until a human at the Mac approves it. The app treats that as a waiting state, not an
error: it keeps the credential, says what to do, and polls on the reconnect schedule.

**Why the handshake can happen at all before the device is known:** `sealed.ts` refuses an unknown
static key, and the token that would vouch for the device travels *inside* the sealed channel. What
opens the door is a pairing window on the Mac — while a pairing token is live, an unknown key is
admitted to the handshake and the `hello` that follows must carry the token. That is the contract
`tools/dev-host.cjs` implements and the desktop's relay listener will have to match.

## The crypto, and why BouncyCastle

`crypto/Sealed.kt` is a byte-compatible port of `src/shared/sealed.ts`: Noise IK, X25519,
ChaCha20-Poly1305, HKDF-SHA256, the same transcript hash, the same nonce layout, the same k1/k2
mirroring.

The platform cannot do it at `minSdk 26`: `KeyAgreement.getInstance("XDH")` is API 33,
`Cipher.getInstance("ChaCha20-Poly1305")` is API 28, and Android has no JCA name for HKDF at any
level. So it uses **BouncyCastle's lightweight API** (`bcprov-jdk18on`, MIT licence) — raw bytes in
and out, no JCA provider installed, no transitive dependencies. Tink would also have been
permissible (Apache 2.0) but its raw primitives live in `subtle`, which is explicitly not a stable
API, and it brings protobuf. GPL was never in scope; it would relicense the app.

**RFC 7748 §6.1 is checked here explicitly.** Node's OpenSSL rejects an all-zero DH result for you
and Android's XDH does not; `Sealed.dh` refuses it in constant time either way.

### Proving it interoperates

A handshake that only talks to itself is worthless, so the port is tested against vectors produced
by *running the TypeScript*:

```sh
node android/tools/gen-sealed-fixtures.cjs     # → app/src/test/resources/sealed-fixtures.json
./gradlew :app:testDebugUnitTest --tests '*SealedInteropTest*'
```

The generator bundles `src/shared/sealed.ts` with the repository's own esbuild and runs it under
Node with the two ephemeral keys pinned, which is what makes a recorded handshake reproducible.
The test asserts the Kotlin side produces the identical handshake message and reply, derives the
identical directional keys and channel binding, and both seals and opens the identical ciphertexts —
including at counters 255, 256 and 257, where a big-endian nonce would still look fine.

## The verification rig

`tools/dev-host.cjs` stands in for a Mac so this module can be worked on without one. It runs the
**real** relay (`relay/src/rendezvous.ts`), the **real** sealed channel (`src/shared/sealed.ts`, as
responder), the **real** protocol, and real ptys through `node-pty`. What is fake is the trust
store — a JSON file and a SHA-256 where the desktop has scrypt, rate limits and revocation.

It is a convenience now rather than the only option: the desktop speaks the relay, and the section
below records what a release build did against it. Keep using the rig for the fast loop, and do not
let it be the last word — the bug that cost a day (80 bytes where the wire wants 81) was invisible
here precisely because the rig re-derived the framing instead of importing the desktop's.

```sh
node android/tools/dev-host.cjs --port 8823
# prints a pairing code containing ws://10.0.2.2:8823 — how an AVD reaches its host
# keys: p = new pairing code · a = approve · l = list · r = revoke all · q = quit
```

Debug builds carry a network-security config permitting cleartext to `10.0.2.2` and localhost only;
release builds have no exception. That is defensible because the payload is sealed before it
reaches the socket — cleartext there costs the metadata TLS would have hidden from a machine that
is already this device's host.

## What is real and what is not

**Real.** The terminal (`terminal-emulator` is a full VT/xterm implementation — colour, wide glyphs,
combining marks, scrollback, selection, IME, pinch to zoom). The crypto, tested against Node's own
bytes. The pairing flow, the approval wait, and the credential, which lives in a blob encrypted by
an AES-256-GCM key held in the Android Keystore — never in `SharedPreferences`. The relay
transport: it connects, handshakes as initiator, and carries the JSON protocol sealed. Attach with
scrollback replay, resume after a reconnect, live status, the key row, copy and paste, automatic
reconnect on network change and on return from the foreground, and a connection indicator that goes
green in exactly one state.

**Verified against the real thing.** On 14 Aug 2026 a **release** APK on a `Pixel_2_API_31` emulator
was paired with Terminal Deck running on a Mac, through **`wss://relay.terminaldeck.dev`** — not a
stand-in host, not loopback. What was exercised, and what proved it rather than what claimed it:

| | proof, from the side that could not be fooled |
|---|---|
| handshake | the Mac's `remote:devices` listed the phone's fingerprint `Y27M-…-ZRLY`, the same six groups the phone was showing; the phone showed the Mac's `Z5Q2-…-ZZA3`, the same six the Mac was showing |
| relay is the live one | `relay.terminaldeck.dev/healthz` went `hosts:0` → `hosts:1` when the Mac was switched on, and `guests:0` → `guests:1` when the phone attached |
| session list | both sessions the Mac had open, with their real cwd and provider |
| attach + replay | the phone rendered scrollback the Mac had produced before the phone existed |
| a real shell | `hostname` typed on the phone answered `Asads-MacBook-Pro-21.local` |
| resize | `stty size` **on the Mac's own pty** answered `5 103` in landscape and `20 61` in portrait |
| Ctrl-C | `sleep 300` interrupted from the key bar's sticky `ctrl`, twice |
| background | 25 s on the home screen, then the same session still took a command |
| network loss | `svc wifi disable` + `svc data disable` → red dot, "Could not reach that Mac", key bar greyed; on restore it re-attached to the same session and the Mac logged a **new** connection id, with the relay still reporting exactly one guest — no leaked channel |

**Still not exercised.** A QR *decode*: the scanner opens and hands what it decodes to the same
parser the typed path uses, but an emulator has no code to point a camera at, so only the deep-link
and typed paths have been run end to end.

**Deliberately guarded.** "New session" sends `{"t":"new"}`, which is *not* in protocol version 1.
The button only appears when `welcome.capabilities` contained `session.create`, because a desktop
whose parser has never heard of a message type closes the socket for `bad-message`. A capability the
desktop did not claim is never exercised.

## Why minSdk 26

Android 8.0. `TerminalView`'s autofill path is `@RequiresApi(O)` throughout, so below 26 a chunk of
the vendored code is dead weight behind version checks. 26 is where `java.util.Base64` and
`java.time` arrive without a desugaring config, and it is comfortably past the releases where TLS
1.2 was off by default — which matters for a transport whose whole job is a socket. The audience is
people running a coding agent on a Mac; the API floor is not what decides whether they can install
this.
