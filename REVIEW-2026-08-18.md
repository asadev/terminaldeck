# His review — 2026-08-18, 6m03s, 726 words

Recorded against **0.4.0 running locally**, after the overnight release. One
recording, four subjects: the remote sidebar, the browser, the web app, and the
copilot on the phone.

**Instruction with it, and it is different from last night:**

> *"Now these are the things that I also want you to take a look and make the
> changes — this time again like before you will fix them, all of them, but **no
> launch, just in local** for all of the things."*

So: build it, prove it locally, and **stop**. No tag, no release, no TestFlight,
no site deploy. He reviews it here first.

---

## 1 · The remote machine group in the sidebar

The screen: a `DESKTOP-DDGMNCV` heading with a monitor glyph, and **every session
row under it wearing the same monitor glyph**.

- **The icon belongs on the machine, not on every session.**
  *"You don't need to give icon of the remote next to all of them — only above
  there, next to the PC, the remote device."* The rows below get **the identical
  icons a local session row has**. Being under the machine's heading is already
  what says they are remote; repeating it on every line says nothing and makes
  the group look foreign.

- **The machine heading gets the same pill and dropdown a project has.**
  *"You will give this exactly same, like this kind of pill to drop, with same
  drop-down, same button — continue last session, new session, or close."*
  Same component, same shape. Not a lookalike.

- **Close on a machine means close its sessions, not disconnect the machine.**
  He talks himself through it in the recording and lands somewhere precise:
  *"Close you will not give — but you can actually give, because it should not
  disconnect the remote account. It will just close all of the sessions from that
  PC. Yeah, you can give this close too, so it will go from here, but whenever
  you want to start, you can start as a new session and you can start from that
  device."*
  So Close ends the sessions and folds the group away; the machine stays paired
  and New session brings it straight back.

## 2 · A remote session is missing the chrome a local one has

- **No tab pill, and it cannot be dragged to the top.**
  *"When I click on any session — the shape of the icon, top bar header is not
  same, and I cannot drag it up there. You cannot have that tab pill here for
  this on the top. So it should be there on the top, just like the normal
  internal local session."*
  The header strip still reads *"Drag a session or a page here to keep it along
  the top"* while a remote session is open, and dropping one there does nothing.

  This was a deliberate decision last night — a remote session was left out of
  `WorkspaceTab` because a ✕ on the pill would promise to end something this
  window does not own. **He has now asked for it directly, so it is overruled.**
  Build the pill; make the ✕ mean what it means for a machine group above.

## 3 · The browser must not know whether a machine is local

The browser's start page lists **"Listening on this machine right now"** — this
machine only, with no way to reach the connected one.

- **Show the remote machine's ports too**, and let him type an address that
  resolves on the remote machine.
  *"When I click on browser there is no way for me to find all the localhost
  pages of the remote device. I should be able to see the available whole ports,
  and I should be able to type and reach the devices which are not here on this
  device but they are from the other remote device."*

- **If typing alone is not enough, give it a device dropdown.**
  *"Maybe give a drop down next to somewhere here with the bar, to choose which
  device we are talking to right now."*

- **One browser, one shape, every machine.** This is the sentence that governs
  the whole item:
  *"Keep the same one browser window for every device — remote device, local
  device, all should have the same type of same browser window with the same
  tabs, everything. **Shape of the application should not be changing for local
  and remote devices.** It should act like that same."*

## 4 · The web app

He is looking at the local build on `127.0.0.1:8090` and notes it and the live
one differ — *"local is different and the live is still different"* — and says to
work from the local one as the newer.

- **The three theme buttons become one icon.**
  *"On the top header bar I still see the same three separate — Auto, Light,
  Dark. You can just give one small icon for switching."* The marketing site
  already has exactly this control; use the same idea.

- **The localhost list still cannot open anything, so it should not be a list.**
  *"I still cannot open the localhost of any of them, so there is no reason to
  give the list here."*

- **What he wants instead**, and he offers two shapes:
  1. *"Maybe we can have one browse bar here and something to browse it, or maybe
     another kind of link to open in our normal browser."*
  2. *"Maybe we can give our domain to them to utilise, to see the localhost —
     like `app.terminaldeck.dev/something`, and they can browse on those links by
     clicking here and it can open to another new tab. So they can review, you
     know — or subdomains or something kind of technology, just like ngrok or
     something. There is this kind of thing that does the same thing."*

  **The second one is a real architectural question and must be answered
  honestly, not quietly skipped.** Publishing somebody's localhost on a public
  URL is a different product from a relay that carries ciphertext it cannot read.
  If it can be done without breaking that promise, build it. If it cannot, say so
  in one plain sentence and ship the first shape, which is a browse bar plus a
  link that opens on the machine — and make that actually work, because the whole
  reason the localhost tab exists is to reach the thing.

## 5 · The copilot on the phone

- **The pill sits over the chat box.**
  *"If we are on copilot on mobile version, now if we want to type here, the pill
  is still there. Why is the pill there if we can type here? Either we will type
  or we will use the pill. So pill should not be inside the chat box — there
  should be a back button to go back on home."*

- **Close the copilot, from the phone, makes no sense.**
  *"Why do we have Close the copilot here? It doesn't make any sense."*

- **Connecting the copilot belongs in Settings, and the pill follows the
  connection.**
  *"Actually connecting copilot should be in the settings. So if the copilot is
  not connecting, this icon should not be inside the pill — then it will be three
  icon pill. Otherwise if the copilot is connected, then four icon pill,
  automatically, like that way."*

## The through-line, again

Two of the four subjects are the same sentence he has now said three nights
running: **the app must not change shape depending on which machine you are
talking to.** A remote session with no tab pill, a browser that can only see this
machine, and a sidebar group that looks foreign are three faces of one thing.
