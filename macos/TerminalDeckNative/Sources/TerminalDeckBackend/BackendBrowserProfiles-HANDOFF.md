# Browser profiles, history, passwords and sign-in handoff

Source written locally on 6 October 2026. No build, typecheck, lint, test, runtime launch, CLI version probe, real credential read or visual check was performed. These services have **not** been wired into the running app. Nothing was installed or released. Only the six new files listed here were created by this lane; existing files and other workers' work were left alone.

## Registered source channels and tools

23 invoke handlers are written:

- 6 profiles: `browser-profile:list`, `create`, `rename`, `avatar`, `activate`, `delete`.
- 4 history: `browser-history:list`, `suggest`, `forget`, `clear`.
- 10 passwords: `browser-password:available`, `state`, `show-file`, `list`, `forget`, `forget-all`, `copy`, `offer`, `answer`, `fill`.
- 3 sign-in: `browser-signin:diagnose`, `handover`, `agents`.

The four MCP definitions retain their exact source schemas and IDs:

| ID / wire name | Actions |
|---|---|
| `browser.history` / `browser_history` | `list`, `suggest`, `forget`, `clear` |
| `browser.profiles` / `browser_profiles` | `list`, `create`, `rename`, `avatar`, `activate`, `delete` |
| `browser.passwords` / `browser_passwords` | `list`, `forget`, `forgetall`, `reveal`, `offer`, `answer`, `fill` |
| `browser.signin` / `browser_signin` | `diagnose`, `handover`, `agents` |

The source base tier is `read`, and actions escalate in the factories before execution. `BackendNativeMCPServer` currently checks only a tool's base tier. Its authenticated authority must therefore supply action-tier grants to these factories, including the caller's **actual** allowed tiers. Never infer authority from `sessionID`, `machineID`, a request field or an arbitrary browser-tab ID.

Factories first ask the authority for the internal read-only `action: "access"` eligibility check before reading private profile metadata. This is not a new public action and must not raise a consent dialog. They then request the concrete action. `fill-target` is also a read-only ownership check. Every actual `fill` carries `ownerMustAnswer: true` plus the exact account/site/profile/tab/document. The returned grant must represent a fresh answer to that exact request, and cannot use an "always allow" preference. Ordinary session callers are refused for all four settings tools. Password tools and external handover additionally require an owner application attended at this desktop; paired-device and unattended grants cannot fill/copy credentials through these tools. Other profile/history actions still check exact profile scope.

## Required exclusive integration edits

These were intentionally not made because existing tracked files belong to other workers.

1. **Backend assembly**: construct one `BackendBrowserProfiles` for the selected explicit app/scratch data root; provide a `requireWriter` closure which fails unless native has exclusive ownership of that exact root and Node has stopped writing these stores. Provide real WebKit `deleteWebsiteData(profileID)`; explicitly call `open()` during authorized runtime bootstrap. Construct one native password adapter and one `BackendBrowserPasswords` with `adapter.makeHost()`, the same root/writer guard, and `requireProfile: { try await profiles.requireProfile($0) }`. Then call `adapter.connect(passwords)` and explicitly `passwords.open()`.
2. **Cipher**: reuse `BackendAccountKeychainCipher` with the **original** app safe-storage identity, not the new helper/executable name. Adapt it with `BackendBrowserPasswordsCipher.keychain(cipher, available: actualSecureStoreReadiness)`. The availability callback is mandatory; it must represent real app-owned Keychain capability, not return `true` blindly. Any initial key provisioning must be an explicit runtime operation. Missing/denied old keys cannot be replaced merely because decrypt failed. Constructors do no Keychain access. The existing safe-storage key and the browser-login file must be carried together; an incompatible machine remains an explicit unreadable fault.
3. **WebKit configuration** (`NativeBrowserTabs.makeConfiguration`): call `adapter.install(into: configuration)` for every regular profile configuration before a WKWebView is constructed. Popup configurations need the same installation; the adapter deduplicates by live user-content controller. The callback `ownership(tabID)` must read the real app-owned tab/profile and active drive-lease state. A person's own capture arming is not an agent lease. Isolated tabs never read/save logins or history.
4. **Tab construction/navigation/close** (`NativeBrowserTab.ensurePage`, native navigation delegate `didCommit`, `NativeBrowserTab.tearDown`): bind each live view to its native tab ID; call `adapter.didCommit(webView, tabID:)` for each committed document; unbind at close and before replacing a view/profile/isolation. The adapter stamps the committed document while the actual agent lease holds the tab, and verifies a private current-document nonce before accepting a message or filling. Do not reuse the previous stamp after replacement. Existing `WKNavigationDelegate` and `WKUIDelegate` remain the owners; do not replace them with this adapter.
5. **History producers**: from native committed navigation call `profiles.remember(profileID: BackendBrowserProfiles.normalizedID(tab.profile), url: committedURL, title: tab.title)` only when `!tab.isolated`. Send later title changes through `retitle`. History has no stored isolated identity; do not normalize an isolated `""` into default. On quit await `flushHistory`; surface `historyWriteFailure` when a write fails. Constructor/open alone never records browsing.
6. **Profile observation**: register channels with a `changed(state)` callback which updates the native profile model and publishes `browser-profile:state` **only to authorized app hosts**. Existing `NativeBrowserTabs.applyProfiles` is private and takes a Foundation value; the integration worker must add an app-owned method that applies `state.wireValue.foundation`, or expose that existing method appropriately. `refreshProfiles`/`choose`/`createProfile` currently use `EngineBridge`: point those invokes at the native registry as part of the global bridge switchover. Normalize only regular default profiles (`""`/`"default"`) to the existing persistent default WebKit store UUID; keep new windows on the active profile and leave existing windows on their original store until an explicit reopen/switch.
7. **Real profile deletion/clear**: the injected deletion callback must stop/recreate or detach pages holding the target store, clear actual website data/cookies/cache through `WKWebsiteDataStore`, and drop the corresponding cached store/identifier only once those operations finish. It must throw on failure. This lane does not delete guessed Chromium directories or fabricate WebKit byte/path counts. Metadata deletion waits for the callback; a failed clear remains a named profile. The broader remote profile-clear result contract from `browser-profile-storage.ts` belongs to the remote/data integration lane and needs meaningful WebKit cleared/held outcomes.
8. **Password UI events**: wire adapter `signInOffer(tabID, safeValue)` to the existing `browser:signin-offer` native banner shape (origin/usernames/message/autoFilled); wire `passwordOffer(tabID, summary)` to `browser:password-offer` with tabID/origin/username only. `NativeSafariPasswords` is the actual producer; no JS password is sent to React, EngineBridge, remote RPC or MCP. Existing Save/Not now buttons must call the native `browser-password:answer`; manager Copy is native-only. Fill must use the exact trusted owning tab/host. The RPC authorizer sees the concrete fill request and is responsible for owner-host or explicitly approved consent, before the service rechecks the committed document.
9. **MCP authority/window resolution**: register factories into the real `BackendNativeMCPServer`; `authorize` must use its authenticated caller table, dynamic grants, per-action tiers, consent, and a revocation-aware `stillPermitted`. `resolveWindow(context, W-or-B-slot, sessionId)` must use the actual authorized native window/session binding table. Do not treat a raw window ID or requested remote session ID as a grant. No metadata/settings tools should be added to an ordinary session's tool allowlist.
10. **Sign-in runtime**: use `NativeSafariPasswords.signInHost(readVersionOutput:)`; supply the native session/provider lane's GUI-safe login-PATH command runner for Gemini version reading, cancellation and the source five-second bound. Version `0.46.0` is the recorded source compatibility floor, not a verified current upstream release. Do not install or upgrade CLIs here. Existing native popup adoption keeps opener and the same WebKit website data store; retain it for embedded OAuth rather than silently diverting every popup.
11. **Lifecycle**: keep the adapter alive with the native browser owner. Close/unbind native pages before `adapter.shutdown()`; shutdown removes only this named script handler and preserves recorder/unrelated integrations. These new factories use invoke registration only, so no `NativeRPCSubscription` tokens are created/discarded here. Any integration subscriptions must be retained by their owner.

## Precise limitations and pending capabilities

- The stores and handler bodies are written, but **zero channels/tools have been proven to serve through the actual app**. All existing-file wiring above is pending; the single combined build/test/visual pass belongs to the coordinator after every lane is integrated.
- Generic external-browser cookie roundtrip is **unavailable** with WebKit's public APIs. `handover` really opens the validated http/https page and returns informational domain hints, while diagnosis/tool text says clearly that no Safari cookies were imported. Remove any existing banner instruction to call retired `browser.import`. Site-specific supported OAuth/callback/token return belongs to the provider/session owner; there is no fabricated return token or universal cookie import here.
- A top-level sign-in form is supported. Cross-origin and same-origin iframe password filling are intentionally refused, matching the existing source's top-frame boundary. Shadow-DOM/custom non-input credential controls are not inferred or silently filled.
- Native profile **metadata** and compatible history are owned here; `WKWebsiteDataStore` ownership, popup session continuity and actual data removal remain the existing native tab/data bridge owner's integration responsibilities.
- `browser-profile-arm.ts` request interception/background response capture and the server-side `browser-profile-storage.ts` clear-result protocol were read for boundary context, not ported by this lane. Network capture is another browser sublane; remote grants/transport are another main lane. Their capture lease must not disable password autofill unless an actual agent holds the page.
- No independent bookmark manager existed to preserve. Old external-Chromium bookmark scanning and extension support are retired by the user's Safari-only direction.
- The old unauthenticated safe-storage format is read with the source version-2 encrypted digest; legacy version-1 is accepted and carried forward only with explicit write ownership. This is compatibility, not a claim that Keychain migration or store integrity has been verified on a machine.
- The factories intentionally require injected authorizers, real platform sinks and a real version runner. They throw or report unavailability when those capabilities fail; no empty successful handlers, Chromium fallback, Node calls or fake secure-store flags were added.

Next step: the exclusive integration worker applies the edits above while retaining the selected root and authenticated grants, then the coordinator performs the single combined compile/test/behavior/visual pass. Until then this is source-only work, not a completed native browser or migration.
